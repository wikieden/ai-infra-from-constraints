系统分层

I01 · "把 8 个请求凑成一批一起算"属于六层里的哪一层？它和"负载"有什么区别？

来源：第 01 章 · 加入 2026-11-05 · 复习记录：

答案

属于 ③ 训练与推理系统。负载（②）是活怎么来：有几个请求、各自多长，由用户决定；凑 batch 是系统对来的活怎么排，由系统决定。

餐厅类比：今晚来几单是客流（②），哪几单一起炒是厨师长排单（③）。

口诀：活怎么来看负载，活怎么排看系统。

I02 · 怎么区分"改模型"（② 模型与负载）和"改算子实现"（④ 算子与编译运行时）？

来源：第 01 章 · 加入 2026-11-05 · 复习记录：

答案

看数学结果变没变。

  • 变了，就是 ②：例如改模型结构让 KV 只存 1/4，模型要存什么、算什么都变了，相当于换菜谱。
  • 没变，只是换了算法实现，就是 ④：例如分块计算、把相邻算子合并，相当于同一道菜换刀法。

口诀：数学变了改模型，数学不变改算子。

请求处理过程

I03 · prefill 和 decode 各做什么？输出 N 个 token 一共要几次前向？

来源：第 02 章 · 加入 2026-11-24 · 复习记录：

答案
  • prefill（预填充）：一次前向处理全部输入 token，存下它们的 k、v（KV 缓存），并得到第 1 个输出 token。
  • decode（解码）：之后每步只送进 1 个 token（上一步的输出），读已有的整份 KV，追加这个 token 的一份，得到下一个 token。

输出 \(N\) 个 token 共 \(N\) 次前向：1 次 prefill + \((N-1)\) 次 decode。结束时 KV 份数 = 输入长度 + \(N - 1\)（最后一个输出不用再送进模型）。

例子（编的）：输入 4 个、输出 3 个 → 3 次前向，KV 4 → 5 → 6。

口诀：读题一口气，写字一个个。

I04 · 模型权重有哪两种搬移？各多久发生一次？

来源：第 02 章 · 加入 2026-11-24 · 复习记录：

答案
搬移 从哪到哪 多久一次
加载 存储 → 显存 实例启动或换模型时，1 次，之后一直驻留
执行时读取 显存 → GPU 计算单元 每次前向都读一遍

所以输出 \(N\) 个 token，权重加载 1 次、读 \(N\) 次。多卡实例还多一种：卡间传中间结果，每层都有。

口诀：菜谱搬一次，每锅翻一遍。

I06 · scale-up 和 scale-out 有什么区别？三种流量里哪种"等不起"？

来源：第 02 章 · 加入 2026-11-24 · 复习记录：

答案
  • scale-up（纵向扩展）：超节点内部的高带宽互联（如 NVLink），让一组卡以低通信开销一起算。例：GB200 NVL72，一个机柜 72 个 GPU 一个 NVLink 域。
  • scale-out（横向扩展）：超节点之间经网卡和交换网络相连，扩大集群范围，开销更大。

三种流量：请求走服务入口；模型文件走共享存储，可以提前加载；计算中的中间结果走加速器互联，每层都有，必须及时到达，下一层才能继续。

口诀：柜内 scale-up，柜外 scale-out。

存储层次与数据流

I07 · 存储层次是在什么和什么之间折中？H100 从寄存器到显存各有多大？

来源：第 03 章 · 加入 2026-11-24 · 复习记录：

答案

在"近"和"大"之间折中：越靠近计算单元越快，但越小、越贵（大楼里每层都修厕所，走得近，但占面积、要维护）。

H100 SXM：寄存器每 SM 256 KB；shared memory + L1 每 SM 256 KB；L2 全卡 50 MB；显存 HBM 80 GB；再往外是 CPU 主存（经 PCIe）。

例：Qwen3-8B 一步要读 15.14 GB 权重，放得进显存，放不进 L2，所以每步都要从显存一块块搬进来。

口诀：厕所修在楼层边，近的小来远的宽。

I08 · 矩阵乘法分块后，从显存读的次数怎么变？限制是什么？

来源：第 03 章 · 加入 2026-11-24 · 复习记录：

答案

\(n \times n\) 矩阵乘法：不分块远处读取 \(2n^3\)；tile 边长 \(t\) 时降到 \(2n^3/t\)。每个读进 shared memory 的数在近处被用 \(t\) 次。

例：\(n = 4\)，不分块 128，\(t = 2\) 时 64。

限制：近处要同时放下两个 \(t \times t\) 块（H100 每 SM 的 shared memory 最多 228 KB），所以 \(t\) 不能无限大。

口诀：读一次来用多遍，分块缓冲写成链。

I09 · prefill、decode、KV 访问、MoE 专家路由，复用范围有什么不同？为什么不能只靠一套自动缓存？

来源：第 03 章 · 加入 2026-11-24 · 复习记录：

答案

按"每读一遍权重被几个 token 用"：

访问 复用
prefill（例：2048 个输入 token） 2048
decode，batch = 1 1
decode，batch = 8 8
KV 只服务本请求，每步整份读一遍
MoE 专家 只有路由到它的 token，平均值掩盖不均匀

差了三个数量级，需求各不相同（算力、带宽、容量、不均匀），所以加速器要把计算单元、局部存储和数据通路按这些访问一起设计。

关键数字

I10 · Amdahl 定律是什么？只加速一部分，整体最多快多少？

来源：第 04 章 · 加入 2026-11-24 · 复习记录：

答案
\[\mathrm{Speedup} = \frac{1}{(1-f) + f/s}, \qquad \mathrm{Speedup} \le \frac{1}{1-f}\]

\(f\)：被加速部分占原总时间的比例；\(s\)：这部分加速几倍。

例：编码快 5 倍，编码占 20% 时整体只快 1.19 倍，占 80% 时快 2.78 倍。

口诀：加速一段看占比，剩下不动是上限。

I11 · 估算一个任务要比较哪四类数字？时间下界和 MFU / MBU 怎么算？

来源：第 04 章 · 加入 2026-11-24 · 复习记录：

答案

容量、计算吞吐、带宽、延迟。

\[M \le M_{\mathrm{cap}}, \quad T_{\mathrm{compute}} = F/\Pi, \quad T_{\mathrm{memory}} = R/\beta\]

\(\Pi\)、\(\beta\) 取峰值时是下界（硬件物理极限）。实际耗时 \(T\)：\(\mathrm{MFU} = F/(\Pi T)\)，\(\mathrm{MBU} = R/(\beta T)\)，都不超过 1。

\(M\) 和 \(R\) 要分开算：存一份，可以读很多次。

例：H100 带宽 3.35 TB/s，读 1 GB 至少 0.30 ms。

I12 · 一张卡能不能放下一个模型，容量预算怎么写？

来源：第 04 章 · 加入 2026-11-24 · 复习记录：

答案
\[M_W + M_{\mathrm{state}} + M_{\mathrm{work}} \le M_{\mathrm{cap}}, \qquad M_W = N b_W\]

权重 + 上下文状态（KV）+ 工作区，多卡要逐卡算。

例：70B BF16 权重 141.11 GB，一张 80 GB 的 H100 放不下；8 比特量化后 73.73 GB，加一个 8192 token 请求的 KV 2.68 GB 和工作区 2.15 GB，共 78.56 GB，刚好放得下。

I13 · GB 和 GiB、bit 和 byte 怎么换算？400 Gbit/s 的网卡传 1 GB 要多久？

来源：第 04 章 · 加入 2026-11-24 · 复习记录：

答案
  • GB = \(10^9\) 字节，GiB = \(2^{30}\) 字节，1 GiB ≈ 1.074 GB；KiB / MiB 同理。相减前先换成同一种。
  • 1 byte = 8 bit；GB/s = Gbit/s ÷ 8。

400 Gbit/s = 50 GB/s，按线速传 1 GB 要 20 ms；实际还要加启动时间、协议开销和链路争抢。

口诀：bit 除以八才是 byte。

I14 · 70B 模型、每参数 1 字节、batch = 1，一步生成要存、读、算多少？

来源：第 05 章 · 加入 2026-11-24 · 复习记录：

答案
\[M_W = b_W N, \quad R_W = b_W N, \quad F \approx 2BN\]

存 70 GB，读 70 GB，算 140 GFLOPs（每个权重乘、加各一次）。\(M_W = R_W\) 只是这一步碰巧相等：下一步存的还是那一份，但要再读一遍。

I15 · 为什么单请求 decode 是带宽说了算？算力翻倍和带宽翻倍各有什么效果？

来源：第 05 章 · 加入 2026-11-24 · 复习记录：

答案
\[T_{\mathrm{step}} \ge \max\!\left(\frac{F}{\Pi}, \frac{R_W}{\beta}\right)\]

读、算能重叠时取较大者。H100 上读权重约 20.90 ms，矩阵计算约 0.1415 ms，读慢约 148 倍。

  • 算力翻倍：下界仍 20.90 ms（只缩短本来就短的计算）。
  • 带宽翻倍或权重减半：下界降到 10.45 ms。

口诀：加算力，白费钱；加带宽、少读数，才见效。

I16 · 批内复用为什么提高吞吐却不缩短每个请求的等待？转折点 \(B_*\) 怎么算？

来源：第 05 章 · 加入 2026-11-24 · 复习记录：

答案

\(B\) 个请求共用一次权重读取：读取时间不变，计算按 \(B\) 增长。\(B = 8\) 时一步仍约 20.90 ms，每个输出分摊约 2.61 ms，吞吐从约 47.9 涨到约 383 token/s；但每个请求都要等整批算完，等待没缩短。

转折点：\(2B_*N/\Pi = b_W N/\beta\)，

\[B_* = \frac{b_W \Pi}{2\beta}\]

H100、\(b_W = 1\) 时约 147.7。之前读取说了算，之后计算说了算。等价说法：算术强度 \(I = 2B/b_W\) 和 \(\Pi/\beta\)（H100 约 295）比。

口诀：一车拉八人，油钱分摊路不短。

I17 · 实测比读取下界慢三倍，差距可能来自哪两种原因？怎么分清？

来源：第 05 章 · 加入 2026-11-24 · 复习记录：

答案
  1. 模型漏项：下界只算了部分工作（如只算权重和 KV 读取，没算其他向量运算和采样）。补上后下界上移。
  2. 系统开销：实现本身的浪费（如 eager 模式逐个提交 kernel、经 Python、驱动和 PCIe，加速器空转；客户端日志占主机时间）。去掉后实测下降。

分清的办法：一次只改一个条件测量。例：Qwen3-8B 下界 8.62 ms，实测 26.5 ms（MBU 33%）→ 关日志 12.1 ms → 只算加速器事件 10.7 ms，只剩两成。

检查顺序：先问模型有没有漏项，再问实现有没有开销。

I18 · 估算一次模型执行，全程在回答哪五个问题？

来源：第 05 章 · 加入 2026-11-24 · 复习记录：

答案

搬什么、搬多少、搬几次、经过哪里、谁在等待。

对应：模型结构决定要哪些权重；位宽和参数量决定大小；批内复用改变读取次数；显存接口提供带宽；执行依赖决定等待。

需求与架构

I19 · 推动架构变化的根本是什么？举 TPU 的例子。

来源：第 06 章 · 加入 2026-11-24 · 复习记录：

答案

比例的改变：需求变化（规模扩大、新负载）或硬件变化（某类器件提升更快），让计算量 : 读取量、带宽 : 处理能力、需求增长 : 单芯片能力这些比例变了，原来合理的分工就不再合算。

TPU：2013 年预测"每位用户每天用三分钟语音搜索，数据中心可能要翻倍"，每日需求 \(Q F_1\) 逼近空闲算力；专用芯片前期投入大，但规模越大越容易回本。TPU v1 2015 年部署，2017 年发表论文。

口诀：比例一变，分工重排。

I20 · SmartNIC 解决了什么问题？光转发要几个核怎么算？

来源：第 06 章 · 加入 2026-11-24 · 复习记录：

答案
\[n_{\mathrm{core}} = \frac{\lambda_{\mathrm{packet}}}{\mu_{\mathrm{core}}}\]

40 Gbit/s、最小帧在线路上 84 字节：\(\lambda \approx 40 \times 10^9 / 672 \approx 5950\) 万包/秒；单核 1000 万–2000 万包/秒，要 3–6 个核，只用来转发。

网速涨得比 CPU 处理包的速度快。Azure 2015 年末起用基于 FPGA 的 SmartNIC，把重复的包处理交给网卡，CPU 留给租户应用，复杂策略仍由主机软件管。

I21 · 卡越来越多时，分析一个多卡方案按哪三步？

来源：第 06 章 · 加入 2026-11-24 · 复习记录：

答案
  1. 每张卡能不能放下它要的数据（逐卡 \(M \le M_{\mathrm{cap}}\)）；
  2. 每张卡要算多少、读写多少；
  3. 按执行依赖，谁要等谁，算总时间。

加卡带来容量和算力，也带来通信和等待。UB（统一互联）的思路是让设备直接访问其他设备的内存，去掉跨主机的软件抽象层。

I22 · 原书列出的五个常见误区是什么？

来源：第 06 章 · 加入 2026-11-24 · 复习记录：

答案
  1. 峰值算力翻倍，速度就翻倍 → 先看是不是算力限制，还要用 Amdahl 定律看上限。
  2. 显存放得下权重，就能支持目标并发 → KV、工作区、运行时预留都占显存，多卡逐卡算。
  3. 比旧实现快三成就算成功 → 先算硬件极限，再查差距来自漏项还是开销。
  4. 上一代成熟的系统可以直接用于新负载 → 每种设计都以当时的比例为前提，先检查比例是否还成立。
  5. 吞吐提高了，每个用户的等待就缩短了 → 吞吐和响应时间要同时报告。

I23 · RNN 和因果 Transformer 处理已知输入时，各要等什么？生成时又多了哪条依赖？

来源：第 07 章 · 加入 2026-11-24 · 复习记录：

答案

RNN 同一层要等前一个位置（\(h_t = f(x_t, h_{t-1})\)），沿位置和层都要串；因果 Transformer 同一层的已知位置可以并行，只等上一层的结果（沿深度）。

生成时多一条跨调用的串行依赖：下一次调用的输入是这次的输出。

口诀：节点算，边上传，箭头定先后。

I24 · 一个 \([m,k] \times [k,n]\) 的投影，参数、运算、权重字节各是多少？\(m\) 和 \(n\) 翻倍各影响什么？

来源：第 07 章 · 加入 2026-11-24 · 复习记录：

答案

\(N_W = kn\)，\(F = 2mkn\)，\(M_W = b_W kn\)。

  • \(m\)（本次 token 数，\(m = BP\)）翻倍：\(F\) 翻倍，权重不变。
  • \(n\)（输出宽度）翻倍：权重和 \(F\) 都翻倍。

prefill 一条 8192 token 的请求 \(m = 8192\)；decode 每条请求只补 1 个，\(m = B\)。

口诀：行数乘权重，权重不随行数涨。

I25 · Qwen3-8B 一层的投影和 FFN 各多少参数？处理 \(m\) 个 token 要多少 FLOPs？

来源：第 07 章 · 加入 2026-11-24 · 复习记录：

答案
  • 注意力投影：\(2 \times 4096^2 + 2 \times 4096 \times 1024 = 41{,}943{,}040\)
  • SwiGLU FFN：\(3 \times 4096 \times 12288 = 150{,}994{,}944\)（占约 78%，BF16 288 MiB）
  • 运算：\(385{,}875{,}968\,m\) FLOPs

一次前向 \(= 36(385{,}875{,}968\,m + 16384\,N_{\mathrm{pair}}) + 2 m_{\mathrm{out}} \times 4096 \times 151936\)：8192 token prefill 约 133.6 TFLOPs，8K 上下文下一步 decode 约 20.0 GFLOPs。

I26 · 有效查询—键配对数 \(N_{\mathrm{pair}}\) 怎么算？注意力运算量和它什么关系？

来源：第 07 章 · 加入 2026-11-24 · 复习记录：

答案

\(N_{\mathrm{pair}} = B\,(PS + P(P+1)/2)\)：长方形是新 token 读旧上下文，三角形是新输入内部的因果访问。

\(F_{\mathrm{attn}} = 4\,n_Q\,d_h\,N_{\mathrm{pair}}\)（Qwen3-8B：\(16384\,N_{\mathrm{pair}}\)）。

\(BP\) 相同不代表注意力相同：拆成两条独立短请求会少掉跨界的配对；前面加上下文会让每个新 token 的配对变多。

例：\(S = 2\)，\(P = 3\) → 6 + 6 = 12。

I27 · 为什么缓存 K、V 而不缓存 Q？每 token 的 KV 怎么算？

来源：第 08 章 · 加入 2026-11-24 · 复习记录：

答案

旧 token 的 K、V 算一次就不变，后来的 token 用自己的 Q 去对它们打分、汇总；旧 Q 已经用完，所以长期保存 K、V。

\(c_{\mathrm{KV}} = 2\,L\,n_{\mathrm{KV}}\,d_h\,b_{\mathrm{KV}}\)。Qwen3-8B BF16：\(2 \times 36 \times 8 \times 128 \times 2 = 147{,}456\) B = 144 KiB；8192 个 token 1.125 GiB。

口诀：问完就走不留 Q，白板常驻 K 和 V。

I28 · 模型数据分哪三类？存储量和访问量有什么区别？

来源：第 08 章 · 加入 2026-11-24 · 复习记录：

答案
  • 权重：多次调用不变、所有请求共用；
  • 上下文状态（KV）：跟着请求保留、持续追加；
  • 临时数据（激活）：算子或阶段里产生、用完释放。

存储量看某一时刻还要留着什么（峰值看同时活着的张量）；访问量看执行过程中累计读写了多少，同一份数据读 \(k\) 次，访问量是存储量的 \(k\) 倍。

I49 · TTFT、完整请求时间、平均 token 间隔各量哪一段？p95 怎么取？

来源：第 14 章 · 加入 2026-11-24 · 复习记录：

答案

\(T_{\mathrm{TTFT}} = t_1 - t_a\)（含排队），\(T_{\mathrm{request}} = t_G - t_a\)，\(\overline{T}_{\mathrm{token}} = (t_G - t_1)/(G-1)\)。缩短排队只改善 TTFT，不缩短已开始后的 token 间隔。

I50 · 等待中的请求为什么也占容量？怎么算？

来源：第 14 章 · 加入 2026-11-24 · 复习记录：

答案

状态占用按空间 × 时间算：\(A_M = \int M(t)\,\mathrm{d}t\)，1 GiB 占 10 秒 = 10 GiB·s。

任务每秒 \(\lambda\) 个到达、每个占 \(M_0\)、平均等 \(\tau\) 秒，稳定时平均占用 \(\approx \lambda M_0 \tau\)（Little 定律）。工具等待越久，同样的容量能服务的任务越少。

I51 · 平均处理能力够了，为什么还会积压？积压怎么算？

来源：第 14 章 · 加入 2026-11-24 · 复习记录：

答案

闲时没用的能力存不到忙时。\(Q_{k+1} = \max(0, Q_k + A_k - \mu_k \Delta t)\)；到达 \(\lambda_w\) 连续 \(\tau\) 秒高于处理率 \(\mu\)：积压 \((\lambda_w - \mu)\tau\)，排空 \((\lambda_w - \mu)\tau/\mu\)。

例题 3-1：两张 RTX PRO 6000 约 5,591 步/秒，后一分钟每秒来 7,471.2 步，积压约 112,792 步，停止后约 20.17 秒排空。

口诀：闲时的力气存不到忙时，超出乘时长就是积压。

I52 · KV 池满时，排队等的是什么？

来源：第 14 章 · 加入 2026-11-24 · 复习记录：

答案

等的是空间不是算力：已有请求的状态没释放，即使有计算单元空闲，新请求也进不来；调度器还可能抢占（暂停已开始的请求、释放 KV，之后恢复或重算）。
